# 受约束生成 vs 确定性编译:信任模型差距审核文档

> 版本:v1(2026-09-08)
> 目的:本文档描述 FlowAgent 当前架构与规范目标架构之间的**信任模型差距**,供独立审核。
> 审核对象:本文档的全部论断、分类学和迁移方案。审核者应优先挑战第 4、6、9 节的事实准确性与完备性。
> 自包含声明:本文档不要求读者预先了解代码库;关键代码以摘录形式内嵌。若审核者有仓库访问权限,可按 §11 的行号索引核实。
> 诚实声明:所有「已实测」标记的论断附有复现方式;未标记的属于推断,审核时应按待验证处理。

## 1. 系统背景(30 秒版)

FlowAgent 是一个 Snakemake 流程编排 Agent 后端(`/home/zj/zj_code_libarary/FlowFrame/FlowAgent/`,TypeScript,~2000 行):

```text
用户自然语言需求
  → LLM(带 SOP system prompt)循环调用 12 个工具:
    query_catalog / query_ports / query_rules / get_rule   # 检索(只读)
    validate_manifests / dry_run / detailed_summary / read_log
    write_gap_log / write_composed / confirm_submit / submit_cluster
```

- rule 库(`rules/*.smk`)与接口契约(`rules/manifests/*.manifest.yaml`)在目标流程仓库内;
- 组合流程写到 `composed/<日期>_<需求>/`,**LLM 生成完整 Snakefile 文本**;
- 提交有三道闸(台账中本任务 dry-run 成功记录 + 用户本人确认记录 + 服务端开关);
- 现有回归:selftest 38 项全过(含 8 个组合文件对抗用例)。

规范文档([总体规划](../../docs/planning/Flow-AI_Rule_Orchestration.md),v1.2)定义的目标架构要求:
**「编译器从合法计划生成固定结构的文件;不让模型自由生成每一个生产文件」(§3.2)**,
组合文件由「确定性编译器」从结构化 PipelinePlan 生成(§4.5/§10.3)。

## 2. 问题陈述:两种信任模型

当前实现与规范目标的核心分歧不是功能缺失,而是**正确性来源不同**:

| | 确定性编译(规范目标) | 受约束生成(当前实现) |
|---|---|---|
| 谁写组合文件 | 编译器(固定模板机械展开) | LLM(生成全文) |
| 正确性来源 | **构造**:Plan 的合法性由 Schema+端口闭合分析前置保证,编译只产生合法产物 | **枚举**:防线(校验器)事后枚举并拒绝已知非法类别,漏一个类别就是洞 |
| LLM 的角色 | 只产出结构化 Plan(选哪些 rule、字面量参数) | 直接决定每一个字节,包括语句顺序、命名、覆盖 |
| 错误模式 | 编译器 bug → **系统性**错误(同因复现,易回归测试) | LLM 幻觉 → **随机**错误(难复现,靠评测集统计) |
| 可审计性 | Plan 是结构化对象,可 diff、可版本化、可机器复核 | 只有台账一句 `reason` 字符串 + 生成文件本身 |

**关键事实:执行层面的科学逻辑(shell/脚本)100% 来自库内已审核 rule**——`use rule` 是引用不是复制,防线保证 LLM 夹带不了自己的代码。所以"pipeline 完全由已验证 rule 拼接"这一预期在**代码层面**成立;差距全部在**组装决策层**(选哪些 rule、参数覆盖、target、config 值)。

## 3. 当前防线:保证了什么、没保证什么

### 3.1 write_composed 的现有校验链(已实测)

LLM 生成的 Snakefile 在写盘前依次通过(`FlowAgent/src/tools/writes.ts` + `src/composed-guard.ts`):

1. **防线 0(正则)**:任何非 `all` 的 `rule X:` 定义被拒(禁复制 rule 本体);
2. **防线 1(语句白名单)**:顶层只放行 `configfile:` / `include:` / `workdir:` / `module X:` / `use rule ... [with]:` / `rule all:`;其余(含顶层 Python `import`/赋值/调用)拒绝并报行号。Snakefile 是 Python,`snakemake -n` 解析即执行顶层代码,且 dry-run 发生在人工确认**之前**——此防线堵的是实测复现过的 P0(顶层 `open(...).write(...)` 载荷曾在 dry-run 阶段真实执行);
3. **防线 2(路径约束)**:configfile/include/workdir/module.snakefile 经 realpath 解析后必须在流程仓库根内且存在(`../` 逃逸、库外绝对路径、symlink 逃逸均拒绝);
4. **防线 3(表达式约束)**:`with:` 块(字段白名单 input/output/params/threads/resources/log/benchmark)与 `rule all` 的 input 只允许字面量与 kwargs,禁止名称引用/调用/属性/dunder;rule all 额外放行 `expand()`(参数仍限字面量);
5. **config schema**:携带 config 副本时按全库 `config_requires` 声明的 JSON Schema(类型/枚举/范围/pattern)校验。

### 3.2 防线**不**保证的(语义正确性)

防线的谓词是「**没有可执行代码**」,不是「**组装科学上正确**」。以下五类错误全部能穿过防线:

| # | 错误类别 | 具体场景(demo 仓库术语) | 现有拦截手段 | 为什么拦不住 |
|---|---|---|---|---|
| E1 | rule 选择错误 | 用户要 R1 报告,LLM 组了 `short_read_qc_r2` 链 | dry_run + confirm 摘要的 dag_tree | DAG 照样解析通过、规模看着合理;依赖人读树时发现 R1/R2 写反 |
| E2 | 链拓扑错误 | 漏 `use rule check_md5`(MD5 门控缺失)→ 直接消费未校验数据 | dry_run | md5_check.tsv 若已存在(上次运行残留),DAG 完整,绿灯 |
| E3 | 参数覆盖错误 | `with: threads: 64`(合法字面量,超节点上限)或 params 覆盖错值 | schema(仅 config 键) | with 块参数无 schema、无上限约束 |
| E4 | config 语义错误 | 物种、链特异性填反——类型对、枚举内、范围中 | schema | schema 拦类型/范围,不拦语义;这正是规范 §4.1 承认的「领域校验」缺口 |
| E5 | target 错误 | `rule all` 指向存在的中间产物而非用户要的交付物 | dry_run + confirm 文件清单 | 解析成功;依赖人核对文件路径 |

**已实测证据**:E1–E5 目前**没有任何自动化测试用例**(selftest 38 项全部是语法层对抗与流程闸门)。换句话说:不存在一个"错误但语法合法的组装被系统拦下"的测试——因为系统里没有负责拦它的组件。

### 3.3 本轮撰写本文档时新实测发现的两个防线缺口(此前未记录)

**G1(缺口,写盘层已实测确认):`with:` 块的 input/output 覆盖值没有路径约束。**
防线 2 只约束 configfile/include/workdir/module.snakefile 四类语句的路径;`with: output: r1_html="/tmp/escape.html"` 是字面量,防线 3 放行。实测:`write_composed` 对指向仓库外绝对路径的输出覆盖**返回 ok=true**(载荷为单输出覆盖;复现方式见 §11.2)。后果:LLM 可把 rule 的读写重定向到仓库外(数据写出逃逸;输入侧同理可读仓库外文件)。本探针的 dry_run 失败仅因通配符一致性问题(只覆盖了两个输出中的一个),属载荷构造问题,不是防线拦截——构造完整的载荷预期可通过。**未实测部分**:完整的执行层逃逸演示(需构造通配符一致的载荷)。
**注**:此缺口的严重度受三道闸限制——提交仍需人工确认,confirm 摘要会展示 target;但 target 显示 `/tmp/...` 依赖人眼发现,且 E5 已说明这不牢靠。

**G2(误伤 bug,已实测确认):防线 3 不接受 Snakemake 惯用的换行命名列表。**
Snakemake 允许:
```python
use rule short_read_qc_r1 from qc as qc_x with:
    output:
        r1_html="..."
        r1_zip="..."
```
(换行分隔、无逗号——这是官方文档的惯用写法)。防线 3 的表达式解析器要求顶层序列以逗号分隔,该写法被拒("记号 r1_zip 位置不允许");同时顶层序列**不容忍尾逗号**(Python 允许)。后果:LLM 按官方文档风格生成的合法组合被误拒,浪费重试轮次,甚至诱导 LLM 换写法绕行。

## 4. 语义错误为什么现在的闸门拦不住(逐闸分析)

- **dry_run**:`snakemake -n` 的谓词是「DAG 可解析且输入有生产者」。E1–E5 全部不破坏 DAG。规范 §1.3 自己承认「dry-run 不证明科学正确」——但在当前架构里,dry-run 是**唯一**的自动化正确性闸门,这个承认等于承认了缺口。
- **config schema**:只覆盖 `config_requires` 声明的键;with 块覆盖(E3)与语义(E4)不在其谓词内。
- **confirm_submit(人工确认)**:摘要现含 job 规模、dag_tree(rule 链)、资源档位——这是目前唯一有机会拦 E1/E2/E5 的环节,但:确认负担完全在人;摘要内容由 LLM 转述(可信度受 prompt 注入影响);确认的是「规模」而非「方案」(规范 §4.4 要求专家审核的是分组/对照/参数合理性,即 AnalysisPlan 对象——**当前实现里这个对象不存在**)。

## 5. 目标方案:Plan + 确定性编译

### 5.1 核心翻转

```text
现在:  LLM 写完整 Snakefile → 防线校验"没夹带私货" → dry_run
目标:  LLM 只交 Plan(结构化) → 校验器验证 Plan(端口闭合/schema/枚举)
                                        ↓ 通过
       编译器按固定骨架展开 → 生成 Snakefile → 防线降级为编译器自检 → dry_run
```

防线白名单(§3.1)恰好就是编译器输出语言的文法——从「校验 LLM 输出」翻转为「编译器生成 + LLM 只出 Plan」,文法不用变,**新增的是 Plan 校验层**。

### 5.2 Plan Schema 草案(供审核)

```yaml
schema_version: "1"
task_id: "20260908_qc_only"
plan_id: "plan-001"
reason: "R1 质控报告:catalog 无单样本交付,组 qc 链"
modules:                              # 允许引用的 module 白名单(编译器据此生成 module 块)
  - alias: qc
    manifest: "03.short_read_qc"      # 必须存在于 rules/manifests/
rules:
  - use: "short_read_qc_r1"           # 必须存在于该 module manifest
    from: qc
    as: "qc_short_read_qc_r1"         # 命名空间前缀(防 AmbiguousRule)
    with:                             # 只允许白名单字段、只允许字面量(与防线 3 同一文法)
      threads: 4
targets:                              # rule all 的 input;展开策略见下
  - pattern: "01.qc/short_read_r1_multiqc/multiqc_r1_raw-data_report.html"
    over: []                          # 空 = 具体 target;非空 = expand 的通配符维度(值来自样本表,不来自 LLM)
config:                               # 组合 config 副本(按全库 schema 校验,已有实现)
  parameter: { threads: { fastqc: 4 } }
```

### 5.3 Plan 校验器(新增的确定性闸门,当前架构完全缺失)

编译前按 manifest 做纯程序化检查——这是把「组装正确性」从 LLM 搬到代码的关键:

1. **端口闭合分析**:对选中的 rule 集合,每个被消费的 port 必须有库内生产者(选中集合内)或标记 `external: true`;**多个不等价生产者时要求 Plan 显式选择**(消除歧义是唯一留给 LLM 的决策点,且被强制记录);
2. **target 可达性**:每个 target 必须匹配某个选中 rule 的 output pattern(已有 `patternToRegex` 实现可复用);
3. **config 覆盖**:选中 rule 的 `config_requires` 并集 ⊆ Plan.config 键集;
4. **with 覆盖合法性**:字段白名单(同防线 3)+ 值的字面量校验 + **新增:input/output 覆盖值的路径约束**(修 G1);
5. **reason 必填**(沿用现有台账审计)。

### 5.4 编译器

固定骨架展开(module 块 + use rule + rule all + configfile/workdir),产出与现在 hand-written 骨架一致的文件;编译后自动跑现有三层防线作为自检(**防线失败 = 编译器 bug**,立即熔断并报错,不落盘)。目录仍 `composed/<日期>_<需求>/` 永不覆盖。

确定性验收:同一 Plan 重复编译,输出字节一致(规范 §10.3 通过门槛)。

### 5.5 迁移路线(不是一步切换)

1. 新增 `compile_from_plan` 工具(Plan 进、组合目录出);`write_composed` 保留;
2. SOP 改为:**catalog 命中与可 Plan 表达的组合一律走编译;编译器表达不了的才允许 write_composed 直写**;
3. 每次直写落一条 `compiler_gap` 缺口事件(复用 gap_log 机制)——直写是编译器文法缺什么的信号,驱动模板长全;
4. 观测直写率趋零后,关闭直写路径(或将其保留为需服务端开关的逃生门)。

## 6. 该方案自身的风险(审核者应重点挑战)

| # | 风险 | 分析 |
|---|---|---|
| R1 | 编译器 bug 是系统性错误:一个模板错误同时污染所有组合,比 LLM 随机错误更隐蔽 | 缓解:防线自检(编译产物必过三层防线)+ golden 测试(样例 Plan → 期望字节)+ 字节一致回归。残余:防线与编译器同源误解时双双失守(共用文法假设) |
| R2 | 表达力天花板:合法但模板外的组合(ruleorder、checkpoint、input function)被驱赶到直写路径,直写率不降反升 | 缓解:compiler_gap 事件显式计量;文法扩展按缺口驱动。未解答:checkpoint 链在 Plan 文法里怎么表达(规范 §1.3 承认 dry-run 展不开 checkpoint)——**这是本方案最大的未解问题** |
| R3 | Plan Schema 过早冻结(规范 §10.3 自己的警告) | 缓解:schema_version + 演进策略;初期只冻结最小集(modules/rules/targets/config) |
| R4 | 端口闭合分析的谓词依赖 manifest 质量:pattern 必填(已实现)但属性兼容(R1 vs R2、raw vs trimmed)仍靠人工维护的 ports.yaml,错误属性会让"闭合"给出错误绿灯 | 这是数据质量风险,不是方案缺陷,但审核者应评估是否把属性校验升级为机器可检查 |
| R5 | LLM 仍决定 Plan 内容:E1–E5 只是被**前移**到 Plan 校验与人工确认,没有消失 | 正确——方案的价值是让错误可被机器谓词检查(闭合/可达/schema)并留下结构化审计对象,而非消灭 LLM 判断。审核者应判断这个定位是否如实 |
| R6 | 两条路径并存的过渡期,SOP 判断"可否 Plan 表达"本身交给 LLM,可能系统性走捷径直写 | 缓解:直写率作为运维指标告警;或反过来默认只开放 compile,直写需服务端开关 |

## 7. 与规范的关系

规范 v1.2 已把当前实现标为「第 3 级参考实现」,但 §3.2 的确定性编译承诺与 §8.2 的三层防线描述之间**没有命名这个中间态**。本文档主张:规范应显式定义「受约束生成」级及其适用边界(受控仓库/过渡期),并给出到确定性编译的迁移触发条件(如:组合请求量阈值、防线绕过事件一次、或 compiler_gap 收敛计划)。否则半年后按规范审计实现,第 3 章承诺与第 8 章验收是两套信任模型。

## 9. 给审核者的问题清单

1. §2 的两种信任模型对立是否成立?「构造正确性 vs 枚举攻击面」的表述有无第三种被遗漏的形态?
2. §3.2 的 E1–E5 分类是否完备?有没有第六类「语法合法但科学错误」的组装缺陷被漏掉?
3. G1 的严重度评估(受三道闸与人工确认缓解)是否恰当?是否应升级为 P0 直接修(在防线 3 中对 with 块的 input/output 值追加路径约束)?
4. G2 误伤是否会在实践中诱导 LLM 绕行(换写法),从而放大而非缩小攻击面?
5. Plan Schema 草案(§5.2)是否够表达当前 demo 仓库的全部合法组合?字段有无缺失(sample 表选择、workdir 策略、include common.smk 的条件)或过度设计?
6. §5.5 迁移路线中「SOP 判断可否 Plan 表达交给 LLM」是否是新的单点(R6)?有无更硬的机制?
7. R2(checkpoint/动态 I/O 在 Plan 文法中的表达)有没有可行的设计?还是应明确排除并保留直写?
8. 端口闭合分析放在编译器内还是独立校验器(§5.3)更利于演进?
9. confirm_submit 的摘要应如何变化,才能把「规模确认」升级为规范 §4.4 要求的「方案确认」(最小代价路径)?
10. §7 的规范修订主张(显式命名中间态+迁移触发条件)是否成立,还是应该直接要求一步到位上编译器?

### 11.2 G1 复现(防线放行 with 块仓库外输出)

在 FlowAgent 目录下,对 demo 副本调用 write_composed,载荷核心:

```python
use rule short_read_qc_r1 from qc as qc_x with:
    output: r1_html="/tmp/flowagent_escape_probe.html"
```

观测:`write ok = true`(防线放行)。对照:同为路径的 `configfile: "/etc/passwd"` 被防线 2 拒绝——差异在于 with 块路径不在防线 2 的约束清单内。

### 11.3 G2 复现(惯用语法误伤)

```python
use rule short_read_qc_r1 from qc as qc_x with:
    output:
        r1_html="a.html"        # 无逗号换行列表(官方文档惯用)
        r1_zip="b.zip"
```

观测:被拒,报「记号 r1_zip 位置不允许(禁止拼接表达式)」;`r1_html="a.html",`(尾逗号)同样被拒。
